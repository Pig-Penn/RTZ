# Architecture

**Component structure.** The mod is split into `addons/` components, each an independent PBO. `main` is the build-time framework (prefix, version macros, CBA/ZEN dependency declarations, `script_macros.hpp`, `script_curator.hpp`) and ships no runtime code; `core` holds the two shared runtime engines; `common` holds shared infrastructure and the shared ZEN context-menu root (`CfgZenContext.hpp`); every other component depends on `rtz_main` (and usually `rtz_common`); anything that draws or streams also depends on `rtz_core`.

**The dependency graph is acyclic**, and every *hard* edge is declared — every `EFUNC`/`EGVAR` call appears in the calling component's `requiredAddons`, and nothing appears there that is not really used. That is a property worth re-checking after any move: a mutual `requiredAddons` pair leaves Arma's load order between the two undefined, and an edge that exists in code but not in config is the same bug waiting for a load-order change to expose it. `hud` ↔ `spotting` was exactly that pair, resolved by moving the two renderers to the component that owns their data.

Three cautions, each of which this claim was once wrong about:

- **External edges count too.** Ten components called `zen_common_fnc_showMessage` while declaring only `zen_context_menu`, and worked purely because ZEN pulls `zen_common` in transitively. `core` had the inversion — it declared `zen_context_menu`, which it never touches, and omitted `zen_common`, which it calls. Grep for `zen_*_fnc_` **and `lambs_*_fnc_`** as well as `EFUNC` when auditing — that sweep was once run for ZEN only, and `rtz_control`'s call to `lambs_wp_fnc_taskReset` sat undeclared behind the gap for as long as the component existed. Distinguish a CALL from a soft READ while you are there: `control` and `spotting` both read `QEGVAR(captive,surrendered)`, but that is a variable name with a default and implies no edge, whereas calling a function the other mod owns does. `rtz_hud` shows the third option — it INLINED `lambs_main_fnc_debugDangerType` rather than acquire the dependency for one debug string.
- **A stringtable key is an edge.** `restrict` listed `rtz_common` solely because its settings file borrowed `ELSTRING(common,DisplayName)` to paper over a missing `STR_RTZ_Restrict_DisplayName` — which also filed every Restrict setting under the *Common* CBA category. If a component's only use of another is a localization key, that is a bug in the component, not a dependency.
- **Soft edges are deliberately NOT declared.** `spotting` reads `RTZ_officerZoneMap`, which `officer` writes. It is a bare `RTZ_`-prefixed global with an empty-map default precisely so `rtz_officer` can be absent, and there is no load-order hazard (written in one postInit, read at tick time). Declaring it would turn an optional feature into a hard requirement. Soft edges belong in a comment at the read site and in the owning `config.cpp` — see `addons/spotting/config.cpp`.

`extras/` holds unbuilt, unchecked components (see its README). HEMTT scans `addons/` only.

Current components:

| Component | Purpose |
|---|---|
| `main` | Build-time framework: prefix, version, macros, CBA/ZEN/LAMBS dependencies. No runtime code. `script_macros.hpp` holds only what is genuinely mod-wide; `script_curator.hpp` holds the Zeus/ZEN *host* constants (display IDCs, `SELECTED_*`, `CHECK_CURATOR_INPUT`, `ACTION_INDEX_*`) |
| `core` | **The two shared runtime engines.** One `Draw3D` handler (`fnc_frameLoop`) draws the whole mod: it resolves the Zeus test, the camera basis and the mouse position ONCE per frame and dispatches to registered renderers, so N displays cost one camera query rather than N. One stream engine (`fnc_selectionPoll` / `fnc_streamServer` / `fnc_streamClient` / `fnc_registerStream`) feeds them: one client selection poll, one server watcher registry, one poll loop, one diffed snapshot event, one dispatch to each stream's registered receiver. Also the shared overlay-toggle halves every toggleable stream reuses. Knows nothing about any particular display. Its **public contract** is `script_macros_core.hpp`, included by absolute path by the components that draw or stream |
| `common` | Shared **infrastructure only**: the selection normalizers (`fnc_collectUnits`/`Squads`/`Vehicles`/`Specialists`), the errand engine (`fnc_approach`, `fnc_clearErrand`, `fnc_progressJob`, `fnc_errandToken`, `fnc_curatorsOf`, `fnc_grantCurators`), presentation helpers (`fnc_classInfo`, `fnc_sideColor`, `fnc_showCountMessage`, `fnc_placementPreview`, `fnc_drawZeusIcon` — vanilla Zeus' own disc/ring/glyph marker, shared by the picker and `place`'s ghosts), the context-menu clean-up, and the shared submenu anchors. Every other component requires this one, so a *feature* parked here is loaded by everyone whether they use it or not — which is why the countermeasures order, the keybind orders and the skill table left for `smoke`, `orders` and `skill` |
| `orders` | Direct curator keybind orders, each guarded by `CHECK_CURATOR_INPUT` and returning whether it consumed the press: camera-to-cursor, stance, fly height, combat mode, open inventory. The unit teleport that used to live here is now `place`, which needed a modal session and a renderer and so no longer fits the one-shot shape the rest of this component keeps to. Owns the three locality-routed receivers those orders send to (`switchStance`, `adjustHeliHeight`, `toggleCombatMode`) and the public per-vehicle `flyHeight` / per-group `holdFire` variables they write |
| `skill` | The built-in per-class skill table (`defaultSkills/`, one file per faction), applied to every spawned man-class unit from a `CAManBase` `InitPost` class event handler. Depends on nothing but the framework |
| `smoke` | Deploy countermeasures: fires the smoke launcher / flare / chaff dispenser of every selected vehicle that has one. Context action at the menu root, config-derived verdicts memoised in `GVAR(cmWeaponCache)` |
| `airstrike` | Order one selected plane to fly a scripted attack run against a curator-drawn point and bearing, delivering a weapon picked from its own pylon loadout. Off by default (`GVAR(enabled)`, Global — the aim session and the executor run on different machines, so they must agree). Split by locality like `path`: the press-drag-release aim session is entirely client-local (one renderer on `core`'s frame loop, no server traffic), and only the order crosses the wire, as one targeted event.<br><br>**Fully on rails**, because the AI will not fly a coherent attack run and will not engage a bare position at all. Three phases on one shared per-frame handler over a bounded registry, created by the first strike and destroyed by the last: an ingress flown by **bounded-rate steering on all three axes** — which replaces Wargame's precomputed parabolic approach paths entirely, since a target behind the aircraft needs no special case when the rotation is simply allowed to take longer — then ZEN's CAS-module `setVelocityTransformation` rail, then a pull-off flown on that same steering before the pilot gets the aircraft back. The ingress converges on the run-in **axis**, not the run-in point, by chasing a carrot that slides along it: steering at the point delivers an aircraft on whatever heading it approached from, which the heading gate rejects, so it sails past and comes round again until the timeout. Rate-limiting pitch and bank rather than yaw alone, and taking bank from the yaw *error* rather than from a turn ratio that saturates through the whole of every turn, is the difference between an aircraft that reads as flown and one that reads as a cursor. Both ends of the rail are eased rather than cut — on final the carrot becomes the mark so the nose is already in the dive at capture, and the pilot inherits a level aircraft rather than one pointed into the ground at attack speed. Geometry and speed are ZEN's (`CAS_DISTANCE`/`CAS_ALTITUDE`/`CAS_SPEED`) rather than Wargame's, whose shorter, steeper run is over in seven seconds behind anything jet-powered; cruise stays derived from the aircraft's own `maxSpeed` but is now bounded at both ends around ZEN's flat figure. The release is the module's trick: an **invisible laser target** planted on the aim point, because `fireAtTarget` needs something to aim at and the AI will not engage coordinates. Accuracy is therefore module-grade; re-guiding projectiles in a `FiredMan` handler, as Wargame does, is the upgrade path and `fnc_release` is separate so it can be taken without touching the engine.<br><br>All teardown routes through `fnc_endStrike`, which restores the AI features **captured at order time** rather than blanket-enabling them, and restores the driver captured at order time rather than whoever is in the seat when it ends. Like `slide`, it applies whichever half is local and targets `QGVAR(release)` at the owner of the other — a strike ended *because* ownership moved would otherwise restore into thin air and leave a plane permanently unable to fly itself. `flyInHeight` is the one thing NOT restored: the engine has no getter for it, so egress sets a sane value from where the aircraft ended up |
| `assemble` | AI orders to assemble/disassemble static weapons and UAVs from backpacks |
| `attack` | Order groups to find and destroy a target via waypoints |
| `battery` | Both halves of the artillery domain, gated separately. **Outgoing** is one context action at the menu root, the replacement for ZEN's `FireArtillery` entry that `common`'s Clean Context Menu removes: the curator picks the target with ZEN's own `zen_common_fnc_selectPosition` — 3D or map, green/red against `inRangeOfArtillery` — a ZEN target module is planted at exactly that point, and ZEN's Artillery Fire Mission dialog opens aimed at it. That entry could pick a position but fired four rounds at zero spread; the dialog has spread, gun count, ammo and rounds but had to be dragged out of the module tree and aimed by hand. This joins the two halves and reimplements neither.<br><br>**A target module, not a grid string.** The dialog's other mode takes a grid, which ZEN resolves through `CBA_fnc_mapGridToPos` with the centring flag set, so a 6-digit grid would move the aim point to the middle of its 100 m square. The logic carries the clicked position exactly, and survives as a named target ("Target Alpha", off ZEN's own `nextName`) that the curator can fire at again. Selecting it needs no ZEN control IDC: the mode and the target's list index are seeded into the public `zen_modules_saved` namespace the dialog already reads its last-used values from, and the dialog is opened down `bi_showCuratorAttributes`'s own path (`BIS_fnc_initCuratorAttributes_target` + `createDialog`).<br><br>Two ZEN `function` config entries are overridden, both the hook `restrict` already uses on ZEN's Arsenal module and both delegating straight to ZEN outside RTZ's own flow. On `moduleCreateTarget`, because creating that class is the only way into the list the dialog's combo reads — `zen_position_logics_fnc_add` keys it on the logic's own `typeOf` — and it would otherwise open ZEN's naming dialog a frame later, a second dialog for something already decided. On the `RscFireMission` display, because ZEN's module displays carry `idd = -1` and override the onLoad that would have parked them in `uiNamespace`, so a config `function` is the only way to reach the display and hang the `Unload` handler that deletes a target the curator did not fire at. Registration is a server round trip, so the index lookup waits on a bounded `waitUntilAndExecute` and takes the target with it on timeout.<br><br>The cost is that ZEN's dialog rebuilds its own gun list from the *anchor* gun (same type, crewed, within 100 m), so the anchor — the gun under the cursor, else the first selected — is what the action really chooses. On by default and Local; nothing crosses the wire until ZEN's own `zen_common_fireArtillery` event.<br><br>**Incoming** is counter-battery: a hostile gun firing paints a zone on every opposing curator's Zeus map showing roughly where it fired from, plus a second circle over where the rounds in flight are about to land. Off by default (`GVAR(enabled)`, Global — the detector runs on the gun owner's machine and the dispatcher on the server, so they must agree). The point is to make a parked battery die: without it, artillery in a PvP session is free damage and never displacing is correct play.<br><br>Detection is the engine's `ArtilleryShellFired` mission event handler, which is where Zeus Wargame's artillery radar starts too — and where the resemblance ends. That event fires **both** on the PC that triggered the action and on the PC where the vehicle is local, so the handler is registered on *every* machine (RTZ guns are local to the curator that spawned them, not to the server) and `local _vehicle` narrows it to exactly one reporter. That gate is what removes any need for a server-side duplicate window — a window would have to be wide enough for network jitter and would then swallow the genuinely distinct rounds of a rocket salvo.<br><br>**The true gun position never reaches a client.** The offset that turns a position into a zone is rolled on the server and only the displaced centre is sent, and the client store is keyed on an opaque server-issued track id rather than the gun's `netId` — a `netId` would let a client `objectFromNetId` straight back to the gun and un-fuzz the whole feature. The roll is `sqrt(random 1) * radius`, not `random radius`: the naive form puts half of every offset inside 0.5r and makes the circle a far better fix than its radius claims.<br><br>A **track is one gun, not one shot**, and its offset vector is reused for every later round — not as an optimisation first, but because a fresh roll per round would jitter the circle once a second and average out to the gun's real position for anyone watching. Between re-rolls the offset is applied to the gun's *live* position, so the true gun is always inside the drawn circle rather than merely near it; the track is re-rolled when the gun displaces past the radius or ages past its lifetime. Three cost decisions follow the same rule as the rest of the mod: the fan-out is coalesced per track behind one bounded `waitAndExecute` (a twelve-round salvo is one or two packets per curator, not twelve), the client's prune is gated on a cached `nextExpiry` so almost every frame pays one float compare instead of a store walk, and the static half of each label is built on receive so no `format` runs per contact per frame. Map-only, so it registers nothing with `core` and declares no edge to it; a mission EH *can* be removed by id, so switched off it costs literally zero — the advantage `spotting`'s un-removable class EH does not have |
| `captive` | Surrender/stand-down toggle (captive, AI disabled, hands-up pose), plus enemy-proximity capture: the prisoner is disarmed, joins his captor's group, transfers to the capturing curators, and both curators are paid half his economy value. Eligibility lives in one `CAN_SURRENDER` macro shared by the condition, collector, modifier and apply guard. `disableAI` does not travel with locality, so a `CAManBase` `"Local"` handler re-applies the state on whichever machine gains a surrendered unit. The capture watch (`fnc_captureTick`) is a shared per-frame engine over a server-side registry, created by the first surrender and destroyed by the last |
| `control` | Squad control: LAMBS reset, squad reload, squad hide/freeze toggle, ownership transfer for units left simulated elsewhere, and the dismount lock that stops a transport's AI crew/cargo bailing out (engine flags plus LAMBS force-eject suppression).<br><br>Also the **remote-control rebuild** (`GVAR(enableRcReset)`, per-curator, default on). A unit released from Zeus remote control comes back unable to aim — engine bug **T179189**: it turns toward a target and never puts the gun on it, which is invisible until it fails to shoot. A remedy ladder run in-game ruled out every cheap fix, *including the LAMBS hard `taskReset` this same component ships*, so `fnc_rcRebuild` deletes the unit and recreates it, which is the only thing that works. Zeus Wargame reached the same conclusion independently and its rebuild is the floor for the carry-over: loadout, rank, face, name, damage, suppression, captive, stance, combat mode, all 17 AI features read with `checkAIFeature` rather than blanket-enabled, `isObjectHidden`, synchronized and attached objects, `vehicleVarName`, group membership and leadership. Per-unit variables ride across on a generic `allVariables` sweep rather than a hand-maintained list, so RTZ's own state and ACE's medical state travel without this component knowing they exist; curator ownership is re-granted through `EFUNC(common,grantCurators)` from the original, so per-officer ownership survives instead of collapsing to the releasing curator.<br><br>**No migration contract and no notification event**, deliberately: CBA's XEH re-runs on `createUnit` so every XEH-registered handler re-attaches for free, and the hand-added per-unit handlers in RTZ either cannot be live on a unit a curator is remote controlling (`path`'s puppet pair, `assemble`'s build/pack pair) or keep their index off the unit entirely (`orders`' gear-animation `AnimDone` handler, in `EGVAR(orders,gearAnimEHs)`). **That last one is the rule the sweep imposes on everyone else: a machine-local handle must never live in an object variable.** `allVariables` cannot tell a fact about the unit from a handle into this machine's state, so it copies the handle to the replacement and broadcasts it public — and any "already installed" guard built on that marker then latches shut for the rest of the mission, silently. `orders` learned this the hard way; see `docs/Knowledge Base/Gotchas.md` §3. Dispatch and the ownership wait in `fnc_rcReset`/`fnc_rcResetApply` are unchanged — the handover is still in flight when ZEN raises the release event, so every machine waits and whichever ends up owning the unit does the work |
| `delete` | Point-free deletion of units, vehicles, bodies and wrecks (context action + keybind); protects players, curator modules and headless clients |
| `dig` | Curator-ordered trench digging: a drag gesture draws a line, the selected engineers walk it, and each grid cell one of them finishes is cut into the **heightmap itself** (`setTerrainHeight`) and walled with scaled `Land_Trench_01_forest_F` blocks. Gated on engineers the way `mine` gates on carrying the magazine. Off by default (`GVAR(enabled)`, Global — the drawing session, the diggers and the builder are on three different machines and must agree).<br><br>A **port** of `ace_trenches_fnc_blockTrench_place`, never a call to it: `rtz_main` declares only `cba_main` and `zen_main`, so ACE is a reference the way ZEN's preview was for `common/fnc_placementPreview`. The port is split into a planner and a builder, where ACE validates and constructs in one pass — which is what forces ACE's own Zeus module to re-enter it with a `_dryRun` flag that returns a different shape. Here `fnc_planTrench` is **pure**, the curator's preview and the server's commit run the *same* function, and a preview cannot promise a trench the server then refuses. One fix travels with the port: ACE's `nearestObjects` check tests the trench's ORIGIN for every cell rather than the cell it is validating — the `nearestTerrainObjects` line above it uses the point correctly — so an obstruction halfway along an ACE line is never seen.<br><br>**Terrain resolution is the constraint the whole design is shaped by.** `setTerrainHeight` moves heightmap *vertices*, 7.5 m apart on Altis, so a foxhole is not expressible and only a line is — which is why ACE's per-unit envelopes deform nothing at all, and why a map whose grid is coarser than `CELL_MAX` (Malden, 12.5 m) is legitimately undiggable. Every height in a plan is resolved **once, off pristine terrain**: neighbouring cells share vertices, so a builder reading the live heightmap would sink each block further depending on which neighbour happened to finish first. `adjustObjects` is **false** where ACE passes true — ACE deforms the whole trench before placing any block and has nothing of its own to disturb, whereas this builds cell by cell and would drag a finished neighbour's blocks down with every later drop. Zeus Wargame passes false for the same reason.<br><br>**No per-frame handler on the server at all.** A cell is a bounded `waitAndExecute` chain guarded by `EFUNC(common,errandToken)`, so a re-tasked digger abandons rather than releasing himself back into formation on top of his new order; the only long-lived state is the capped `GVAR(trenches)` registry, which holds the original vertex heights a fill-in order would restore. The cap drops the OLDEST record rather than refusing a new dig, so digging never stops working — what is lost is only the ability to fill that one back in. A digger's machine is told an id and an index, never the plan: CBA events copy their payload, so a record handed across would be mutated there and the server's own copy would never see a block appear. Blocks are created with the bare two-argument `createSimpleObject`, which is **global** (CBA's `fnc_createNamespace` branches on exactly that; the third argument is what makes one local), so they reach every client and JIP like any networked object. Whether the *terrain* change reaches a JIP client the same way is the one thing not established from source — the registry is what would make a replay possible if it does not. |
| `economy` | Zeus point costs: categorization, cost registration, per-curator coefficients (`defaultCosts/`). Also the **income clock**: the size of and time until the next payout, written into the clock bar's mission-countdown slot — dead on a mission with no time limit. That bar is vanilla (the `"Loop"` case of `\a3\ui_f_curator\ui\scripts\RscDisplayCurator.sqf`), and it rewrites all three fields every frame behind a `clocktime` deadline it keeps on the assigned curator logic; `fnc_incomeClockTick` **leases** the bar by renewing that deadline past its own tick, which is why it must write elapsed time and daytime itself, and why ceasing to renew is the whole teardown. The payout schedule otherwise lives only in the server's income PFH, so the server publishes the next payout time; the size is derived locally from two global settings |
| `loot` | AI orders to sweep nearby bodies, weapon holders, crates and unmanned vehicles and improve their loadout. Gear is classified through a lazily memoized `BIS_fnc_itemType` wrapper (`fnc_itemCategory` / `fnc_weaponScore`), and a take is gated on slot, score and *feedability* only — a rifleman takes a machine gun or a live AT tube if it beats what he holds and he can find a magazine for it. `fnc_unitRole` survives as the gate on the three items the ENGINE itself restricts (medikit, toolkit, mine detector), read from the unit's *config* loadout so a stripped medic is still a medic. `fnc_lootPlan` is pure and decides what one unit would take from one target — run before dispatch, so nobody is marched to a target they have no use for — while `fnc_lootStep` executes it one step at a time, since engine take actions cannot be stacked and `rearm` must land last. Errand ownership rides entirely on `EFUNC(common,errandToken)`; there is deliberately no separate claim flag |
| `hud` | The selection info dialog, unit/vehicle tags, and the destination/target overlays — **its own** displays, with their gatherers and renderers. Not "every display": `supply`, `mine` and `spotting` each own theirs. Owns no engine — it is a consumer of `core` like any other component. Requires `rtz_orders` for one read: the vehicle overlay reports the fly-in height that component's keybind commands.<br><br>The two head-tag families are ONE mechanism with two declarations (`fnc_startTagSystem`), not two implementations: `GVAR(tagSystems)` holds a record per live system — visibility, built-entry cache, dirty flag, renderer, demanded slices — and one `CBA_SettingChanged` watcher serves all of them. They were a pair of near-identical start functions with a visible/cache/dirty global triple each, which forced every consumer (the toggle, the context label, both receivers, both renderers) to read those globals behind `isNil` guards, because either system may be switched off in settings. Absence from the map replaced the guards. What the two genuinely share is factored out rather than duplicated: `fnc_tagEntryTail` composes and measures the line, `fnc_drawTagLine` renders it with the LAMBS tactic and the status word each split off in its own colour at measured boundaries, `fnc_tagAnchor` resolves what either kind of entity hangs its tag above (and owns the `[]`-position gotcha both had to know). The *renderers* stay separate — de-confliction and icon layout are infantry-only, and merging would produce one function branching on entity kind |
| `mine` | Mine placement and detection drawing |
| `officer` | Officer auras and area buffs with cooldowns and monitors |
| `repair` | AI orders to repair vehicles |
| `place` | **Unit placement: a modal session for repositioning the Zeus selection**, opened and committed on one keybind (Shift + T, inherited from the one-shot teleport it replaces). Ghosts seed in formation at the cursor — which alone reproduces the old order, tap for tap — and each can then be hold-dragged onto whatever surface the cursor is over. Enter or a second press commits, Escape cancels, and Zeus closing cancels. Entirely client-local: `curatorSelected` and the cursor are UI-local and `setPosASL` has global arguments and effects, so nothing crosses the wire and there is no receiver to register.<br><br>**It exists because the order it replaces could not place a unit indoors, and no amount of better aiming could have made it.** Two separate things forced a roof. The cursor was resolved with intersections on, so the ray stopped at the first geometry it met; and then the result's height was *discarded* and each unit's target re-traced down a vertical column from 200 m up, taking the HIGHEST mostly-flat surface. The second is what made the case hopeless — a curator with the camera inside a room, cursor squarely on the floor, still got the whole squad lifted onto the roof, because the re-trace never saw the aim.<br><br>So the mode does not snap, and deliberately owns no notion of a building: no `buildingPos`, no floor picker, no interior heuristic. **The curator chooses the storey by flying the camera**, and `EFUNC(common,cursorSurface)` answers with the nearest mostly-flat surface along the ray from it — the roof from outside, that room's floor from inside — and the commit takes the ghost's position **verbatim**. The one place inference survives is the seed, where `EFUNC(common,surfaceStack)` returns every floor in the column at a unit's offset and the one NEAREST the cursor's own height wins, so a squad seeded around an interior cursor lands on that floor. Pointing at a roof still puts them on the roof; only the case that was unreachable changed.<br><br>Range is gated **per unit** now, measured from where each stood when the session opened — ghosts move independently, so the old single test against the selection centre would let one unit be sent across the map as long as the average stayed short — and it is *shown*, as a red ghost, rather than reported after the chance to fix it has gone. COMBAT units are refused at open rather than at commit, for the same reason. Ghost models are capped per client (`GVAR(ghostModelMax)`); above it the session is unchanged but the markers stand in alone, since the model is the only part whose cost scales with the selection. Hover is resolved in the renderer, which already holds the camera basis and mouse from `core`'s frame context, and every label and colour is built once at seed time — a session can stay open for as long as a curator likes. All teardown routes through `fnc_endPlacement`, which deletes both the models and the Logic helpers they ride: attachment does not make deleting the parent delete the child, and a leaked helper leaves a simulation-disabled soldier standing in the world, invisible to Zeus because it was never curator-editable |
| `path` | Path planning: a modal drawing session where each selected unit gets a drag handle and the curator traces the path it should take, in the 3D view or on the Zeus map, committing every path at once. Off by default (`GVAR(enable)`). A cleaned-up port of Zeus Wargame's Path Planning. Split cleanly by locality — the whole planning half is client-local (one renderer on `core`'s frame loop, one map Draw handler, one tick, no server traffic at all) and only the commit crosses the wire, as one targeted event per unit. Paths are drawn dense and executed sparse: `fnc_reducePath` resamples a several-hundred-point traced line down to corner-preserving legs, and hands back the original index of each survivor so anything carried *per index* can be remapped onto them. How sparse depends on the executor — a `doMove` chain wants legs the AI can navigate between, a scripted executor wants every corner — so each profile carries two spacings and `fnc_commitPaths` picks between them (`PROF_COMMIT_SPACING` / `PROF_SCRIPTED_SPACING`).<br><br>**Three executors**, resolved per record where the unit is local and driven by one shared tick over a bounded registry (`fnc_followTick`, same shape as `slide`), with two cadences inside it: movement on every wake, conditions on a half-second stagger. *Land vehicles* execute on `setDriveOnPath` and the engine drives, with a bounded re-assert for the case the engine silently drops the path. *Men* are **puppets** by default (`GVAR(infantryExecutor)`): `fnc_setPuppet` disables `MOVE` and `ANIM`, walks them on a directional animation resolved by `fnc_moveAnimation`, and the tick steers the hull by hand — which is the only way a drawn line gets walked as drawn. The two reactions that costs them are given back rather than written off: `fnc_combatPause` breaks the path to engage and resumes after (bounded, unlike Wargame's), and `fnc_openDoors` opens what they walk into (cached per building *class*). *Aircraft and boats* fly their own line (`fnc_flightTick`): attitude and velocity set directly, speed chased toward a cruise that is scaled down for how hard the path bends within the next few legs, with a helicopter flare and an AI-owned landing at the end. `setDriveOnPath` does nothing at all for Air or Ship, and a `doMove` chain gives the AI a destination but no line. Both scripted executors are refusable and fall back to a `doMove` chain re-asserted only when `expectedDestination` shows the formation FSM stole the order.<br><br>Nothing is ordered at commit: `fnc_startFollow` only builds the record, and `fnc_launchFollow` issues the first order from the tick at `FOLLOW_START_AT` — which buys a re-task its settle without a spawn per order. Facing spans (the stretches a curator marks by holding Alt, after aiming the handle with a Shift-drag) are a sparse span list on `PATH_FACING` rather than a payload per point, read through a monotonic cursor in the follow record so the lookup is an integer compare per tick. Every restore is owned by `fnc_endFollow`, never by the `AnimDone` handler that does the looping. **Aircraft trailing in formation** get a lateral and vertical echelon offset, because nothing keeps a flight in formation along a scripted move chain — on the ground the offset is still refused, since groups already do that themselves |
| `restrict` | Locks servicing attribute edits (health/fuel/ammo/skill/cargo/vehicle damage) outside the curator's editing zones (any curatorEditingArea, not just officer-planted ones, and honouring curatorEditingAreaType); each row is gated against exactly the selection subset it writes to; sliders stay visible as info |
| `slide` | Order AI-driven land vehicles to drive in a straight line to a position (keybind) — forward or backward, chosen per vehicle from the sign of the cursor's projection onto its own fore-and-aft axis, so one keystroke can send half a selection forward and half of it back. AI cannot be commanded to reverse at all, and a forward `doMove` answers a different question (it pathfinds, prefers roads, may turn around), so both directions take the same route: the driver is taken off the navigation stack and the hull is pushed with `setVelocity` along an axis captured at order time. Direction is resolved once, in `fnc_orderSlide`, into a travel axis and a speed — nothing downstream branches on it. One shared per-frame engine (`fnc_slideTick`) drives every maneuver from a `GVAR(active)` record registry and is created/destroyed with the first/last one; only the velocity push and arrival test run per frame, the abort conditions are throttled. All teardown routes through `fnc_endSlide`, which restores the driver captured at order time — not whoever is in the seat when it ends, and which applies whichever of the vehicle/driver pair is local while targeting `QGVAR(release)` at the owner of the other. Every restore it performs takes a local argument, so a maneuver ended *because* ownership moved would otherwise tear down into thin air and leave the hull with its parking brake released. Called `reverse` until it grew the forward half — a "slide" here is specifically the direct `setVelocity` push, never the pathed movement `path` and `orders` do |
| `spotting` | AI spotting, end to end: the knowsAbout detection pass, contact callouts, the client stores, **and** the drawing — `fnc_drawSpots` / `fnc_drawRcIndicator` in the 3D view, `fnc_initCuratorDisplay` on the Zeus map. The renderers lived in `hud` until they were moved here; reading six of this component's globals from over there made the two mutually dependent with only one direction declared |
| `supply` | Supply vehicles repair/refuel/rearm the friendly vehicles parked around them, through the engine's own `actionNow ["Repair"/"Refuel"/"Rearm", source]` rather than a scripted ramp — so the truck's `getRepairCargo`/`getFuelCargo`/`getAmmoCargo` deplete natively and there is no RTZ-owned supply counter. Vehicles only: a vanilla ammo truck carries a vehicle rearm pool and no infantry magazines, so there is nothing for one to hand a rifleman. The job is a **monitor**: it watches the deficit close, and re-stamps the overlay's duration when the client's straight line drifts. Owns a supply-lines stream on `core`'s engine |

**Component skeleton.** New features are added as new components under `addons/`, following the same skeleton:
- `config.cpp` — `CfgPatches` (name, `requiredAddons`, version) plus includes for `CfgEventHandlers.hpp` / `CfgContext.hpp` / settings
- `script_component.hpp` — defines `COMPONENT`/`COMPONENT_BEAUTIFIED`, includes `script_mod.hpp` then `script_macros.hpp`, then `core/script_macros_core.hpp` if it draws or streams, and holds that component's visual/tunable `#define`s. A constant belongs to whichever component *uses* it — if two components need one, it goes in a header one of them owns and the other includes, not in `main`
- `XEH_PREP.hpp` — `PREP(fncName)` for every function in `functions/`, compiled once via `XEH_preInit.sqf`
- `XEH_preStart.sqf` / `XEH_preInit.sqf` / `XEH_postInit.sqf` — CBA Extended Event Handler lifecycle hooks (declared in `CfgEventHandlers.hpp`)
- `functions/fnc_*.sqf` — one function per file, standard SQF header comment (Author/Arguments/Return Value/Example/Public)
- `initSettings.inc.sqf` — CBA settings (included from `config.cpp`); `initKeybinds.inc.sqf` for CBA keybinds
- `stringtable.xml` — ALL user-facing text goes through stringtable entries (`CSTRING`/`LSTRING` macros), never hardcoded strings. Omit the file entirely if the component has no user-facing text (`skill` has none); `hemtt check` reports unused keys

**Where does a new feature go?** Its own component, not `common`. The test is whether anything *else* calls it: `common` is for code with real external callers, and every component requires it, so a feature parked there is loaded by everyone who will never use it. Small is not a reason to merge — `attack` is 307 lines and `delete` is 371.

**Drawing and streaming go through `core`.** Two rules, both there to stop the duplication this architecture was built to undo:

- **Never call `addMissionEventHandler ["Draw3D", …]`.** Register a renderer instead:
  `[QGVAR(myThing), ELINKFUNC(mycomp,drawMyThing), RENDER_WORLD, 50] call EFUNC(core,registerRenderer)`.
  `RENDER_WORLD` renderers receive the shared frame context (camera position, camera-right/up, mouse, clock, view distance — indexed by the `CTX_*` macros) and are skipped while the Zeus map covers the 3D view. `RENDER_UI` renderers drive controls on the curator display, receive the display (or `displayNull`), and are called on Zeus-closed frames so they can tear their controls down. Unregister when the display is switched off — that is what makes it free, and with every renderer gone the loop never builds a camera basis. The only sanctioned exception is a short-lived, camera-free draw such as `common/fnc_placementPreview`.
- **Never build a second selection poll or server gather loop.** Declare a stream — **both halves in one call**:
  ```sqf
  [
      STREAM_MINE, LINKFUNC(gatherMine), SRC_HULLS, QEGVAR(core,pollInterval), 2,
      ELINKFUNC(core,receiveOverlay),                 // or your own receiver
      [                                               // omit for an always-on feed
          LINKFUNC(drawMine), QGVAR(enableMineDisplay),
          [LLSTRING(MsgMinesHidden), LLSTRING(MsgMinesShown)],
          [LLSTRING(ActionDrawMines), LLSTRING(ActionHideMines)],
          COLOR_MINE
      ]
  ] call EFUNC(core,registerStream);
  ```
  The engine owns the watcher registry, the per-stream cadence, the resolve of each selection slice (`SRC_UNITS` / `SRC_VEHS` / `SRC_HULLS`, resolved once per watcher per tick), the send diff, the targeted push, and the dispatch to your receiver. **Declare the wording, never hardcode it in the engine** — the toggle statement and `modifierFunction` are shared (`EFUNC(core,toggleOverlay)` / `EFUNC(core,overlayActionModifier)`) and read what you registered. `rtz_supply` is the worked example of a component owning a stream from outside `core`.
- **Consumers of a selection slice must declare demand:** `[QGVAR(myDisplay), [SRC_UNITS]] call EFUNC(core,setDemand)` (third argument `true` if you need the expensive per-unit intel), and `[QGVAR(myDisplay), []]` to withdraw. The poll streams a slice only while someone asks, so a display that forgets gets no packets — and one that never withdraws keeps the feed alive for nothing. Declare it from the same place that registers or unregisters the renderer, so the two cannot drift: a live renderer with no demand draws from a store the server stopped filling, and a live demand with no renderer is a packet per entity per tick pushed to nobody. That second half is not hypothetical — the vehicle slice was ungated for exactly that reason until `setDemand` took a slice list instead of one boolean per feed. `SRC_HULLS` is **not** a demand: hull demand is an overlay being switched on, which `EFUNC(core,toggleOverlay)` already records in `GVAR(activeStreams)`, and giving that one fact two owners is how they come to disagree.
- **The payload rules live in `EFUNC(core,buildReport)`, not at the call sites.** Both senders — the poll's tick and `reportNow` — go through it. The two hand-written copies it replaced were required to agree, one carried a comment saying so, and when they differed the failure was silent and permanent: the poll finds its own payload differs from the baseline the other wrote and re-subscribes every single tick for the rest of the mission.
- **To force an immediate re-subscription, call `[] call EFUNC(core,reportNow)`** — never build the payload or write `EGVAR(core,reported)` yourself. That baseline is the poll's private diff state, and hand-rolling around it is a trap that has already been sprung twice: `hud`'s selection dialog spelled the subscribe event `QGVAR(watch)` inside its own component (so it expanded to `rtz_hud_watch`, an event with no handler) *and* wrote the baseline first, which made the poll suppress the genuine send too — the dialog's intel rows stayed empty on first open. The same block also re-derived the hull-slice gate with a comment warning it had to match `selectionPoll` exactly. `reportNow` builds the payload from the engine's own state by the engine's own rules; pass `true` only when you need the detail flag *before* your `setDemand` call has run.

All of `core`'s shared contracts (`RENDER_*`, `CTX_*`, `SRC_*`, `SEL_MAX_*`, `VEH_SIDE_OK`, `SIDE_NUM`) live in **`addons/core/script_macros_core.hpp`**, and a consuming component pulls them in from its own `script_component.hpp`:

```cpp
#include "\x\rtz\addons\core\script_macros_core.hpp"
```

These used to sit in `main/script_macros.hpp` on the belief that "component headers are not visible to each other". They are — an absolute PBO path resolves any component's header from any other, and ACE3 relies on this: ten medical components include `\z\ace\addons\medical_engine\script_macros_medical.hpp`. Keeping the contract with the component that implements it means `attack`, `loot` and `economy` — which neither draw nor stream — no longer parse it, and a `CTX_*` index can change without touching the one addon every other addon depends on.

What *does* belong in `main`: the `GETVAR`/`SETVAR` family, `VEHICLE_TYPES`, the `PREP` override, and (in `script_curator.hpp`) the Zeus/ZEN host constants, since those describe the environment rather than any RTZ subsystem. ZEN structures its own `main` the same way.

**Nothing in `core` may name a specific display.** That is the invariant the whole split exists to protect: it was violated by a `case STREAM_UNIT` in the snapshot receiver, by hardcoded renderer/setting tables in preInit, and by the poll reading two of `hud`'s globals to decide what to stream — which is what forced `mine`, `spotting` and `supply` to depend on a component full of tags and dialogs. If you find yourself adding a stream id or a display's variable name to `core`, the contract is missing something instead.

Gatherers report **absolute** times, never ages or progress figures: an age changes every tick and defeats the send diff, while a frozen timestamp diffs away and is aged client-side each frame — which also makes the readout climb smoothly between polls instead of stepping.

**ZEN integration.** Context menu actions are declared per-component in `CfgContext.hpp` (`zen_context_menu_actions`); `common/CfgZenContext.hpp` holds the shared RTZ context-menu root. Toggle-style actions keep their label in sync (Show ↔ Hide) via a `fnc_modifyAction` in their component. `common` provides the selection-normalization helpers (`fnc_collectUnits`, `fnc_collectSquads`, `fnc_collectVehicles`) that expand ZEN selections (e.g. vehicles → crew) into flat lists — entry points should go through them.
